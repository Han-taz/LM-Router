# 학습 없는 라우터의 구성 후보

기준일: 2026-09-06 · 상태: **설계 후보, 구현 미확정** · [문서 안내](../README.md)

## 공통 구조 제안

최신 권고는 [신규성·개발 타당성](../research/novelty-and-feasibility.md)과 [구현 재사용 계획](implementation-reuse-plan.md)에 있다. 아래 구조 자체의 신규성을 주장하지 않는다. vLLM protection·Weave planner를 가까운 경쟁 기준선으로 추가했으며, 여러 gateway를 직렬 결합하기보다 하나의 실행 계층 위에서 정책을 분리해 평가하는 방향이다.

```text
에이전트의 다음 모델 요청
  → 현재 실행 상태와 필수 기능 추출
  → 모델·제공자 카탈로그에서 불가능한 후보 제거
  → 후보 정책으로 기본 선택
  → 캐시·전환·예산 조건 검사
  → 모델/제공자에 요청 전달
  → 실제 사용량·도구 결과·검증 결과 기록
  → 다음 단계 상태 갱신
```

라우터의 출력은 모델 이름 하나보다 `모델, 제공자 제약, 선택 이유, 제외 이유, 예상 비용, 유지/전환 여부, fallback 후보`가 적합하다. 실제 선택된 모델은 실행 응답으로 다시 확인한다.

이 구조는 기능 검사·정책·상태·전송을 분리하자는 프로젝트 제안이다. 참고 구현: [R01](../references/sources.md#r01), [R02](../references/sources.md#r02), [R04](../references/sources.md#r04).

### 구현 조사에 따른 구체화

Switchyard는 규칙·기존 LLM judge·선택 주기를 교체하는 정책 계층, Weave는 새 추천과 현재 모델을 비교하는 캐시 경제성 계층의 참고가 된다. 두 저장소를 추가한 뒤 **능력·진행에 따른 후보 추천과 유지·전환 판단을 별도 모듈로 다룬다**는 제안의 근거가 구체화됐다. [R06](../references/sources.md#r06), [R07](../references/sources.md#r07)

이는 학습된 Weave 추천기를 채택하거나 두 저장소의 코드를 복사한다는 뜻이 아니다. 초기 규칙 추천과 캐시 정책을 독립적으로 비교하고, 코드 도입은 API 안정성·라이선스·검증 결과를 보고 결정한다.

## 비교할 세 후보

| 후보 | 선택 로직 | 필요한 데이터·호출 | 강점 | 약점 |
|---|---|---|---|---|
| A: 규칙 + 유지 정책 | 수동 작업 분류, 필수 기능, 비용, 진행 상태 | 모델 명세·가격·현재 로그 | 단순·재현 가능·추가 LLM 호출 없음 | 애매한 의미·새 작업에 약함 |
| B: 규칙 + 선택적 LLM 판단 | A로 결정하기 어려운 때만 rubric 기반 판단 | 기존 범용 LLM 호출 | 의미와 상황을 더 풍부하게 해석 | 판단 비용·지연·비결정성 |
| C: 규칙 + 과거 사례 검색 | 유사 작업의 결과·비용을 참조 | 성능 이력·임베딩·사례 저장소 | 가중치 학습 없이 경험 재사용 | 데이터 구축·갱신·유사도 오류 |

연구 순서 제안: A를 먼저 기준선으로 정의하고, B의 추가 비용 대비 개선을 평가한다. C는 데이터 의존 방식을 허용할 때 별도 실험한다. A의 규칙만으로 품질이 충분하다고 가정하지 않는다.

추가 조사에서 C의 직접 비교군으로 **kNN utility 대 Avengers-Pro**, 무라벨 출력 memory를 허용하는 별도 후보로 **Smoothie-Train**을 확인했다. 수동 semantic 예시 경로는 모델 능력을 자동 추정하는 C와 구분한다. CP-Router·CARGO는 현재 모델을 먼저 실행해 얻는 신호가 필요하고, BoundaryRouter는 direct/agent 실행 방식까지 선택하므로 초기 세 후보에 무조건 합치지 않는다. 조건·출처는 [추가 방법론 비교](../research/alternative-routing-methods.md)를 따른다.

## 캐시를 고려한 유지·전환 정책

1. 현재 모델이 필수 기능·컨텍스트 제약을 만족하는지 먼저 검사한다. 만족하지 않으면 유지 선호보다 제약이 우선한다.
2. 현재 모델과 다른 후보의 앞으로 들 비용을 비교한다. 이미 사용한 비용은 기록하되 전환의 미래 이득과 혼동하지 않는다.
3. 다음 호출의 입력만 계산하는 근시안적 추정과 남은 단계까지 가정하는 추정을 구분한다. 남은 단계 수를 모르면 여러 시나리오로 민감도를 본다.
4. 전환 비용에는 대상 모델의 prefix 처리, 판단 호출, 상태 변환, 예상 재시도·검증 비용을 반영한다. 계산 항목을 두 번 더하지 않는다.
5. 비슷한 후보가 번갈아 우세해지는 경우 현재 모델을 유지하는 여유 구간을 둔다. 임계값·최소 유지 단계 수는 아직 정하지 않는다.
6. 지원 기능 부족·진행 정체·명확한 작업 유형 변경·가용성 문제가 생기면 재평가한다. 단순 도구 5xx는 우선 환경 오류로 분류한다.

세션 stickiness는 성공을 보장하는 기능이 아니다. OpenRouter의 현재 운영 사례처럼 재평가와 기존 모델 선호를 함께 둘 수 있다. [D05](../references/sources.md#d05)

## 상태 전달 계약

라우터가 받을 전체 요청, 선택기가 읽을 판단용 입력, 실행 모델에 보낼 이력을 구분한다. 최근 사용자 문장만 전달하면 생략·지시어를 해석하지 못할 수 있다. 입력 후보와 실제 구현의 추출 동작은 [라우터 입력과 대화 맥락](router-input-and-context.md)에 정리했다.

- 대화·도구 호출·도구 결과·사용자 제약·검증 결과를 공통 실행 상태로 관리한다.
- 제공자별 API 메시지 형식·추론 블록·호출 ID 변환은 adapter 책임으로 둔다.
- 긴 상태를 요약해서 넘기면 요약 비용과 정보 손실을 평가한다.
- 서버 전용 대화 ID나 암호화된 reasoning 상태를 다른 모델/제공자가 동일하게 해석한다고 가정하지 않는다.
- 이미 실행된 도구를 전환 후 중복 실행하지 않도록 실행 이력과 도구 결과를 보존한다.
- 사용자 본문·검색 결과·도구 출력은 라우터 운영 지시로 신뢰하지 않는다. 예산·허용 모델·데이터 지역 제한은 신뢰된 설정에서 강제하고, 판단용 LLM의 추천이 이를 우회하지 못하게 한다.
- 클라이언트가 제어하지 못하는 제공자 내부 도구 단계까지 교체할 수 있다고 가정하지 않는다.

호환성 근거: [D03](../references/sources.md#d03), [D08](../references/sources.md#d08).

## 초기 기능 범위 제안

첫 구현은 작은 후보 모델 풀, 한 종류의 에이전트 harness, 명확한 성공 판정이 있는 작업군에 한정한다. 웹 UI·결제·다중 테넌트·마켓플레이스·자가학습 정책은 현재 조사에서 구현 필요성이 정해지지 않았다.

모든 호출을 프록시로 감싸는 방식과 에이전트 미들웨어로 넣는 방식을 비교해야 한다. 미들웨어는 phase·도구·진행 정보를 얻기 쉽고, 프록시는 기존 앱에 연결하기 쉽지만 요청만으로 실행 의도를 추정해야 할 수 있다. 공통 정책을 어느 통합 방식에서도 호출할 수 있게 분리하는 것이 제안이다.

## 아직 결정하지 않은 사항

| 결정 | 현재 상태 | 필요한 근거 |
|---|---|---|
| 주력 작업군 | 미정 | 코딩·조사·구조화 추출 중 무엇을 먼저 검증할지 |
| ‘학습 없음’의 범위 | 별도 라우터 학습 제외는 확정 | 기존 LLM 판단 호출, 과거 성능표·임계값 최적화 허용 범위 |
| 모델·제공자 풀 | 미정 | 도구·가격·컨텍스트·한국어·가용성 검증 |
| 품질 하한·시간 한도 | 미정 | 사용할 서비스의 성공 기준 |
| 승격 뒤 유지 범위 | 후보만 존재 | 한 번 승격 후 유지 대 제한적 왕복 실험 |
| 승격의 의미 | 미정 | 기존 상태 인계 대 재시작의 비용·성공 비교 |
| 통합 지점 | 미정 | 사용할 harness와 API 호환성 |
| 정책 파라미터 | 미정 | 개발 세트에서 진단 후 평가 전 동결 |

이 항목이 미정이라는 이유로 현재 문서조사를 중단하지 않는다. 구현을 시작할 때 사용자 맥락과 실험 범위에 맞춰 순서대로 결정한다.
