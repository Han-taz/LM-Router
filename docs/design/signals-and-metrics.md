# 라우터의 입력 신호와 평가 지표

기준일: 2026-09-06 · 상태: 설계 제안 · [문서 안내](../README.md)

## 먼저 구분할 세 가지

1. **제약:** 지원하지 않는 도구·컨텍스트·출력 형식 때문에 선택할 수 없는 후보를 제거한다.
2. **입력 신호:** 지금까지 관찰한 정보로 후보를 비교한다. 실제 성공 확률이나 미래 출력 길이는 대부분 모른다.
3. **평가 지표:** 작업 실행 후 정책을 비교한다. 최종 정답·미래 도구 결과를 현재 단계의 입력에 넣으면 정보 누출이다.

지표 목록보다 먼저 정할 것은 작업의 성공 조건, 허용 품질 저하, 비용·시간 한도다. 정답 판정이 없는 상태에서는 ‘가장 저렴하면서 충분한 모델’을 검증할 수 없다.

아래 표는 프로젝트용 제안이다. 기능 필터는 [R01](../references/sources.md#r01), 단계별 실행 평가와 캐시 회계는 [P02](../references/sources.md#p02), 세션 고정은 [D05](../references/sources.md#d05)를 참고했다.

## 선택 전에 사용할 정보

| 묶음 | 필드 예시 | 얻는 시점·방법 | 사용 목적과 한계 |
|---|---|---|---|
| 필수 기능 | `required_tools`, `vision`, `structured_output`, `api_mode` | 요청과 도구 스키마, 공식 모델 명세 | 불가능한 후보 제거. ‘도구 지원’과 ‘해당 도구를 잘 사용함’은 다름 |

| 가격 | 입력·캐시 읽기·캐시 쓰기·출력 단가, 가격 버전 | 공식 가격표 또는 제공자 카탈로그 | 단일 ‘토큰 단가’로 축약하지 않는다. 긴 입력 할증·서비스 티어 포함 |
| 요청 유형 | 코드 수정, 추출, 탐색, 수학, 요약, 언어, 필요한 검증 | 수동 규칙 또는 선택적 범용 LLM 판단 | 필요한 능력을 설명하는 신호. 난이도·성공 확률의 정답이 아님 |
| 실행 상태 | `phase`, `step_index`, 최근 도구 결과의 종류 | 에이전트 상태·이벤트 | 원래 질문과 현재 필요한 작업이 다를 수 있음 |
| 맥락 충족 | 최근 role별 메시지, 활성 작업, 참조 메시지 ID, `history_truncated`, `context_insufficient` | 원래 요청·애플리케이션 이력 저장소 | ‘이건’의 대상이나 이전 제약을 누락했는지 확인. 입력 구성과 맥락 충족 판단은 별개 |
| 진행·복구 | 연속 검증 실패, 동일 호출 반복, 새 증거 유무 | 도구·테스트 결과와 실행 기록 | 모델 역량 부족과 도구 서버 장애를 구분. 실패 한 번으로 즉시 승격하지 않음 |
| 캐시 추정 | 후보별 prefix 식별자, 마지막 사용 시각, 추정 재사용 길이, TTL | 애플리케이션 기록과 과거 usage | 선택 전에는 예측값. 실제 제공자 내부 캐시 존재를 보장하지 못함 |
| 전환 상태 | 현재 모델, 마지막 전환 단계, 전환 횟수, 유지 기간 | 세션 상태 | 빈번한 왕복과 반복적인 초기 처리 비용 억제 |
| 예산·시간 | 남은 작업 예산, 남은 시간, 호출 한도 | 누적 청구·시계·설정 | 부족하면 무조건 저가 모델로 보내지 말고 가능한 완료 방식·중단 조건 판단 |
| 운영 상태 | 최근 지연, timeout·429·5xx 비율, 가용성 | 완료된 요청의 이동 집계 | 제공자 선택·fallback. 처음에는 unknown으로 두고 추측하지 않음 |
| 검증 가능성 | 테스트·스키마·계산 결과·근거 검증기 유무 | 작업 정의 | 저가 모델 시도 후 검증·재시도가 적합한 작업인지 판단 |

추가 고려: 시스템 프롬프트·도구 정의·reasoning 설정의 변경도 캐시 경계에 영향을 준다. ‘현재 모델이 같다’라는 플래그만으로 cache hit를 예측하지 않는다. [D01](../references/sources.md#d01), [D03](../references/sources.md#d03)

### 공개 구현에서 얻은 구체적인 신호 후보

Switchyard Stage는 `severity`, `spinning`, `exploring`, `production_intensity`, 최근 테스트 통과와 컨텍스트 압축 여부를 사용한다. 고정 규칙으로 추출 가능한 에이전트 상태의 예다. 다만 코드 편집 없이 조사만 하는 작업에서 ‘쓰기가 없음’을 정체로 해석하면 잘못 승격할 수 있으므로 작업군에 맞춰야 한다. [R06](../references/sources.md#r06)

Weave planner에서 추가로 참고할 필드는 `CachePrefixKnown`, `CacheablePrefixTokens`, `PriorOutputTokens`, `PinCacheCold`, `ExpectedRemainingTurns`다. 재사용량 0과 미관측을 구분하고, 캐시 가능한 prefix와 매번 새로 처리하는 tail, 출력 비용을 나눠 비교한다. TTL 경과나 직전 usage로 다음 hit를 확정할 수는 없다. [R07](../references/sources.md#r07)

로그에는 `fresh_recommended_model`과 `final_selected_model`도 구분한다. 둘이 다르면 캐시 유지·기능 제약·승격·fallback 중 어떤 규칙이 바꿨는지 남겨야 추천기와 전환 정책을 따로 평가할 수 있다.

## 관측값과 추정값을 혼동하지 않기

최근 질문만·첫 질문+최신 질문·최근 대화 창·작업 상태+관련 이력의 차이는 [라우터 입력과 대화 맥락](router-input-and-context.md)을 참고한다. 라우터의 판단용 토큰 수로 실행 모델의 비용·컨텍스트 한도를 계산하지 않는다.

- 정확히 관측 가능한 것: 이미 사용한 토큰, 완료된 호출의 실제 모델, 현재 이력, 직전 도구 오류, 이미 지불한 비용.
- 추정해야 하는 것: 후보별 다음 출력 길이, 다음 요청의 cache hit, 남은 단계 수, 후보의 최종 작업 성공률.
- 처음부터 알 수 없는 것: 선택하지 않은 모델을 썼을 때의 실제 성공 여부와 총비용.

`quality_score=0.8`이나 sigmoid로 변환한 규칙 점수는 검증 전에는 ‘성공 확률 80%’가 아니다. 신뢰도라는 이름을 붙여도 보정된 확률이 되지 않는다. 값마다 `observed / estimated / unknown`과 근거를 기록한다.

성능 이력을 이용해 점수를 자동으로 갱신하거나 정답 데이터로 임계값을 탐색하면, 신경망 학습은 없어도 데이터 적응·최적화가 들어간다. 이를 순수 수동 규칙 실험과 분리한다.

## 비용 계산

입력 토큰은 겹치지 않는 범주로 정규화한다.

```text
call_cost = (fresh_input_tokens × fresh_input_rate
           + cache_read_tokens × cache_read_rate
           + cache_write_tokens × cache_write_rate
           + billed_output_tokens × output_rate) / 1,000,000
           + applicable_request_fees

episode_cost = sum(all_billable_model_call_costs)
             + tool_fees + other_billable_services
```

- 모델 호출 합계에는 실행·라우터·검증 역할의 모든 시도와 재시도를 포함한다. 이미 호출 합계에 든 재시도 비용을 별도로 다시 더하지 않는다.
- 제공자 원본 usage도 보존한다. 어떤 API는 input에 cached input을 포함하므로 단순 합산하면 중복 청구 계산이 된다.
- 생각하는 토큰이 output 총계에 이미 포함되면 다시 더하지 않는다. 캐시 쓰기에 별도 요금이 없는 API도 있다.
- 동일 요청에서 캐시 읽기와 새 구간 쓰기가 함께 발생할 수 있다. ‘hit/miss’ 두 값만으로 회계하지 않는다.
- 제공자 청구 비용이 있으면 이를 보존하고, 자체 계산값과 차이를 확인한다. 가격 스냅샷·서비스 티어·장문 할증 조건을 같이 남긴다.
- 예측용 가격과 실행 후 실제 비용은 별도 필드다. 이미 발생한 비용과 앞으로 들 비용도 분리한다.

캐시 과금은 제공자·모델 세대마다 달라진다. 공식 기준은 [D01](../references/sources.md#d01), 에이전트 평가에 적용한 사례는 [P02](../references/sources.md#p02)다.

## 작업 후 비교할 지표

| 중요도 | 지표 | 정의·해석 |
|---|---|---|
| 필수 | 작업 성공률 | 성공 작업 수 / 평가 대상 작업 수. 작업 유형별 성공 판정 정의가 선행 |
| 필수 | 총비용·작업당 비용 | 실패·중단·라우터·검증·재시도 비용 포함 |
| 필수 | 성공 1건당 비용 | **전체 평가 비용 / 성공 작업 수**. 성공한 실행들만의 평균 비용과 다름. 성공 0건이면 정의 불가로 보고 |
| 필수 | 전체 완료 시간 p50/p95 | 사용자 요청부터 종료까지. 모델 응답 시간 외에 라우팅·도구·검증 포함 |
| 필수 | 기능·프로토콜 오류율 | 지원하지 않는 모델 선택, 잘못된 도구 형식, 응답 계약 위반 |
| 필수 | 예산·시간 초과율 | 사전에 정한 제한 초과 또는 제한으로 인한 종료 |
| 진단 | 캐시 읽기 토큰 비율 | 정규화한 cache read / 전체 입력. 제공자별 분모 정의 고정 |
| 진단 | 캐시 쓰기 비용·전환 비용 추정 | cache hit가 높아도 비싼 모델 반복 읽기 때문에 전체 비용이 높을 수 있음 |
| 진단 | 모델·제공자 전환 횟수 | 각각 집계. 전환 수 자체를 최소화하는 것이 최종 목적은 아님 |
| 진단 | 단계 수·도구 호출 수·복구 횟수 | 단가 절감이 더 긴 경로로 상쇄되는지 확인 |
| 진단 | 라우터 비중 | 라우터 비용 / 총비용, 라우터 시간 / 전체 시간 |
| 진단 | 승격 빈도·승격 후 성공 | 정책을 설명하는 지표. 승격의 인과적 효과는 별도 대조 실험 필요 |
| 진단 | 비용·시간의 꼬리 분포 | p95·최대·상위 비용 작업이 차지하는 비율. 평균만 보면 반복 실패가 숨을 수 있음 |

‘라우팅 정확도’는 정답 모델 라벨을 정의할 수 있을 때만 보조적으로 쓴다. 여러 모델이 충분히 잘할 수 있으며, 단일 단계의 충분함과 전체 작업 성공은 같지 않다.

## 최소 로그 계약 제안

원문 전체를 무조건 저장할 필요는 없다. 재현에 필요한 상태와 민감정보 처리 정책은 별도로 설계한다.

```text
식별: episode_id, session_id, step_id, request_id, parent_call_id
버전: policy_version, model_catalog_version, price_snapshot, harness_version
결정 전: current_model, requirements, budget_remaining, progress_signals
후보: eligible_models, excluded_reasons, estimated_costs, cache_estimates
결정: fresh_recommended_model, selected_model/provider, decision_reason, switch_reason, rule_id
실행 후: resolved_model/provider, raw_usage, normalized_usage, actual_cost
시간: router_ms, model_ttft_ms, model_total_ms, tool_ms, episode_elapsed_ms
결과: tool_error_kind, verifier_result, retry_count, final_status
```

첫 실험에서는 필수 지표와 이를 계산할 로그를 먼저 갖춘다. 후보별 성공 확률 예측기를 만드는 것은 이 프로젝트의 현재 무학습 제약과 별도의 결정이다.
