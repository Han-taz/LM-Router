# 라우터 입력과 대화 맥락 구성

확인일: 2026-09-06 · 상태: 구현 조사 + 프로젝트 제안, 실행 미검증 · [문서 안내](../README.md)

## 출발 질문

사용자가 ‘이건 어떻게 하는 거야?’라고 물으면 마지막 문장만으로는 대상도 필요한 능력도 알 수 없다. 모델 라우팅 입력을 `query: string` 하나로 한정하지 않고, 현재 질문을 해석할 수 있는 대화와 실행 상태를 함께 다룰 필요가 있다.

특히 ‘이건’이 이전 **assistant의 제안**을 가리키면 사용자 메시지만 모아도 맥락이 빠진다. 도구 루프에서는 새로운 사용자 질문 없이 도구 결과만 추가되기도 한다.

## 구분해야 할 세 가지 입력

| 입력 | 포함할 수 있는 내용 | 목적 |
|---|---|---|
| 애플리케이션/프록시가 받는 요청 | 메시지 이력, 도구 정의·결과, 첨부 자료, 출력 조건, 세션 정보 | 실제 실행 요청과 상태 확보 |
| 선택기가 읽는 판단용 입력 | 관련 대화 창, 현재 작업 요약, 도구 진행 신호, 후보 명세 | 적합한 모델 선택 |
| 선택된 모델에 보내는 실행 입력 | 작업 수행에 필요한 원래 이력·도구·지시문 | 실제 답변·도구 호출 생성 |

전체 요청이 프록시에 도착했다고 선택기가 전체를 읽는 것은 아니다. 반대로 판단용 입력을 짧게 만들었다고 실행 모델의 입력도 짧아지는 것은 아니다. 비용·컨텍스트 한도 검사는 축약된 판단문이 아닌 **실제로 실행 모델에 보낼 요청**을 기준으로 한다.

클라이언트가 최신 문장과 `session_id`만 보내면, 애플리케이션이 해당 세션의 이력을 조회해 합치는 단계가 필요하다. ID 자체에 대화 내용이 들어 있는 것은 아니다. 제공자 전용 대화 ID로 서버 내부 상태를 이어가는 경우에도, 독립 라우터가 그 내용을 자동으로 볼 수 있다고 가정하지 않는다.

## 실제 구현은 무엇을 읽는가?

### Switchyard: 기본 task 입력과 window 입력이 다르다

앞서 확인한 고정 ref의 `llm_class.rs`를 추가 조사했다. [R06](../references/sources.md#r06)

- 기본 `task_messages()`는 첫 사용자 메시지와 마지막 사용자 메시지를 선택한다. 서로 다른 중간 assistant 답변은 이 경로에서 제외된다.
- `recent_turn_window=N`을 설정하면 첫 사용자 작업과 그 뒤의 최근 대화 메시지를 포함한다. 이때 assistant 답변과 도구 이력도 들어갈 수 있다.
- `window_start()`는 도구 결과만 남고 대응 도구 호출이 잘리는 것을 피하도록 창의 시작을 조정한다. 따라서 단순히 배열의 마지막 N개를 자르는 것과 다르다.
- 정규화된 client system/developer 지시문은 judge용 지시문과 별개다. 공식 문서는 이 client 지시문을 judge에 그대로 보여주지 않는다고 설명한다.
- Stage는 의미 판단용 질문만 사용하는 대신 도구 이력에서 진행·오류 신호를 추출하는 별도 경로다.

**해석:** 첫 질문+마지막 질문도 중간에 등장한 ‘두 번째 방법’, ‘방금 제안한 구조’를 놓칠 수 있다. `classify_trigger`로 판단 주기를 정하는 것과 `recent_turn_window`로 판단에 보일 맥락을 정하는 것은 독립된 문제다.

### Weave: 프록시 상태와 기본 cluster 임베딩 입력이 다르다

고정 ref의 `features.go`, `service.go`, `scorer.go`를 연결해 확인했다. [R07](../references/sources.md#r07)

- 요청에서 `PromptText`, `OnlyUserMessageText`, 도구·이미지 유무 등의 입력을 추출한다.
- `OnlyUserMessageText`는 마지막 한 문장만이 아니라 이력의 사용자 텍스트를 모은 것이다. assistant·system·도구 결과는 제외한다.
- `ROUTER_EMBED_ONLY_USER_MESSAGE`의 문서 기본값은 `true`다. 해당 설정과 비어 있지 않은 사용자 텍스트가 있으면 기본 cluster scorer에 그 텍스트를 준다.
- scorer는 `TailTruncate()`를 적용한다. 기본 `MaxPromptChars=1024`지만 실제 구현은 UTF-8 경계를 보존한 **바이트 기준** tail 절단이다. 의미상의 1,024자·토큰과 같지 않다.
- 프록시는 별도로 role·도구 정보가 있는 `ConversationMessages`도 구성한다. 따라서 기본 cluster 입력의 한계를 HMM 등 모든 정책이 동일하게 가진다고 일반화하지 않는다.

**해석:** 사용자 텍스트만 쓰는 기본 경로는 assistant가 소개한 대상을 가리키는 후속 질문에서 근거를 놓칠 수 있다. 전체 텍스트로 설정을 바꿔도 tail 절단으로 오래된 선행사가 빠질 수 있다. 이는 코드 구조에서 예상되는 실패 가능성이며 이번 조사에서 성능을 재현한 결과는 아니다.

### 추가 비교: Bifrost·Arch-Router·failover 연구

- Bifrost의 semantic complexity는 최신 또는 최근 N개 user 메시지를 embedding한다. assistant/system을 넣지 않으므로 N을 늘리는 것만으로 assistant의 제안을 가리키는 ‘이건’을 해결하지 못한다. tool continuation의 tier 재사용은 입력 이해와 별도 기능이다. [R12](../references/sources.md#r12)
- Arch-Router는 policy 설명과 대화를 받으며, 논문 사례에 생략된 후속 질문도 있다. 따라서 대화 맥락을 받는 발상 자체는 기존 연구다. 다만 이 논문의 정책 매칭 정확도가 실제 선택 모델의 성공률·가격 최적성을 뜻하지는 않는다. [P29](../references/sources.md#p29)
- ContinuityBench는 실패 후 latest-user-only 전달과 full-history 전달을 비교한다. 이력을 보존해야 하는 이유를 보여주는 제한된 실험이지, 현행 gateway가 모두 마지막 질문만 보내는 증거는 아니다. text 중심·단일 실패 조건을 native tool/reasoning state 호환성으로 확대하지 않는다. [P18](../references/sources.md#p18)

## 입력 구성 후보 비교

| 방식 | 이점 | 한계 |
|---|---|---|
| 최신 질문만 | 작고 저렴한 기준선 | 생략·지시어·도구 후속 요청에 취약 |
| 첫 작업 + 최신 질문 | 원래 목적과 최신 변경을 유지 | 중간 assistant 제안·주제 전환을 놓칠 수 있음 |
| 역할을 보존한 최근 대화 창 | 직전 제안·정정·도구 결과를 직접 볼 수 있음 | 멀리 있는 지시 대상은 창 밖으로 나감 |
| 활성 작업 상태 + 최근 대화 + 관련 과거 구간 | 오래된 제약과 최근 진행을 함께 보존 | 상태 갱신·검색·요약의 비용과 오류 관리 필요 |

마지막 방식을 현재 프로젝트의 후보로 제안한다. 하지만 초기에는 요약 생성 LLM 없이 **구조화된 기존 상태 + 최근 원문 메시지 + 필요 시 과거 메시지 조회**로 시작할 수 있다. 규칙·임베딩·LLM 중 어느 선택기를 쓰더라도 ‘입력에 관련 맥락이 있는가’는 별도로 평가한다.

## 설명용 입력 예시

아래는 프로젝트 내부 자료형의 예시이며, 특정 제공자 API나 이미 구현된 스키마가 아니다.

```json
{
  "session_id": "s-1",
  "episode_id": "e-2",
  "latest_user_message_id": "m3",
  "recent_messages": [
    {"id": "m1", "role": "user", "text": "PostgreSQL에서 동시 주문 때문에 재고가 음수가 돼."},
    {"id": "m2", "role": "assistant", "text": "트랜잭션 안에서 SELECT FOR UPDATE로 해당 재고 행을 잠그는 방법이 있어."},
    {"id": "m3", "role": "user", "text": "이건 어떻게 하는 거야?"}
  ],
  "agent_state": {
    "current_model": "balanced-model",
    "phase": "awaiting_answer",
    "recent_tool_results": [],
    "history_truncated": false
  }
}
```

이 맥락이라면 ‘이건’의 후보가 이전의 행 잠금 제안임을 판단할 수 있다. 후보 모델 명세, 실행 요청의 토큰 추정량, 필수 기능, 예산·캐시 상태는 별도 신뢰된 필드로 함께 제공한다. 원문 메시지는 판단 대상 데이터이지 라우터 운영 정책을 바꾸는 지시가 아니다.

## 학습 없이 처리하는 흐름 제안

1. 실제 메시지 이력과 실행 상태를 확보한다. 세션 pin만 있고 이력이 없는 경우를 구분한다.
2. 현재 활성 작업·최근 사용자 변경과 최근 assistant·도구 메시지를 토큰 예산 안에서 구성한다. 오래된 첫 질문을 현재 작업으로 영구 고정하지 않는다.
3. 지시 대상이 빠졌을 가능성이 있으면 창을 넓히거나 참조 ID로 이전 메시지·파일·이미지를 가져온다. 한국어 ‘이건’, ‘그거’, ‘두 번째 것’ 같은 패턴은 경고 신호이지 완전한 해석기가 아니다.
4. 수동 규칙으로 기능·작업·진행 상태를 판단한다. 의미 해석이 필요한 경우에만 기존 LLM의 맥락 판단을 추가 후보로 둔다. 별도 학습은 없지만 추론 비용이 발생한다.
5. 여전히 모호하면 `context_insufficient`로 표시한다. 더 강한 모델로 바꾸기만 해서는 누락된 정보를 복원할 수 없다. 실행 에이전트가 확인 질문을 할지 결정하도록 전달한다.
6. 추천 모델과 현재 모델을 캐시·비용 정책으로 비교하고, 선택된 모델에는 작업에 필요한 실행 이력을 전달한다.

‘이건’을 풀어 쓴 독립 질문으로 재작성하는 방식도 선택지다. 다만 재작성 자체가 해석이며 잘못된 대상·제약을 만들어낼 수 있다. 사용한다면 원문·근거 메시지 ID·불확실성을 같이 보존하고, 단순히 질문 하나를 재작성했으니 완전히 해결됐다고 보지 않는다.

## 캐시·비용·안전

- 로컬에서 메시지를 선택·구조화하는 작업만으로 LLM 입력 토큰 요금이 추가되는 것은 아니다. 외부 판단·임베딩·요약 API를 호출하면 해당 비용을 포함한다.
- 판단용 요약을 만들 때마다 실행 모델의 원래 system 메시지나 과거 대화 prefix까지 덮어쓰지 않는다. 판단용 입력과 실행용 입력을 분리하면 불필요한 캐시 훼손을 피할 수 있다.
- LLM judge를 쓰면 안정적인 정책·후보 명세와 변하는 요청 맥락을 구분하되, 실제 캐시 지원·적중은 제공자별로 확인한다.
- 대화 창을 줄일 때 도구 호출·결과 쌍과 역할을 보존한다. 파일명·이미지 참조만 남았다면 선택기가 필요한 내용이나 최소 기능 요구사항을 실제로 확보했는지 확인한다.
- 사용자·도구 텍스트가 허용 모델·예산·데이터 지역 정책을 덮어쓰지 못하게 한다. 요약에도 원문 역할·출처·갱신 버전을 남긴다.

## 평가할 사항

동일 선택기·모델 풀을 두고 위 네 입력 방식을 비교한다. 마지막 문장은 동일하되 이전 맥락만 달라지는 쌍, assistant 답변을 가리키는 질문, 긴 이력·주제 전환·사용자 정정·도구 후속 결과를 포함한다.

맥락의 대상·필수 제약 보존 여부와 `context_insufficient` 처리, 라우터 입력량·판단 비용·시간, 최종 작업 성공률·전체 비용을 함께 본다. 정답 모델 하나를 임의로 지정하기보다 실제 작업에 필요한 능력을 누락했는지와 전체 실행 결과를 평가한다.
