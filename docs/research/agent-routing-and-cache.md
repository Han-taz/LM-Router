# 에이전트 라우팅 단위와 프롬프트 캐시

확인일: 2026-09-06 · 상태: 연구 요약 · [문서 안내](../README.md)

## 조사 질문과 잠정 결론

사용자 요청 하나가 여러 모델 호출·도구 실행으로 이어질 때, 모델을 처음에 고정해야 하는가, 매 단계 다시 선택해야 하는가?

두 방식 모두 가능하다. 현재 근거는 ‘항상 고정’이나 ‘항상 전환’의 보편적 우월성을 입증하지 않는다. 이 프로젝트의 첫 후보는 **요청별 기본 모델 + 실행 중 재평가 + 캐시를 고려한 제한적 전환**이다. 이것은 연구를 종합한 제안이며 실측 결과가 아니다.

## 서로 다른 결정 단위

| 방식 | 선택 시점 | 주요 장점 | 주요 비용·한계 |
|---|---|---|---|
| 작업별 고정 | 사용자 요청 시작 | 구현 단순, 캐시와 이력 유지에 유리 | 최초 질의로 보이지 않던 난이도에 대응하기 어려움 |
| 단계별 선택 | 다음 모델 호출 직전 | 도구 결과·진행 상태·모델별 강점 반영 | 라우팅·전환·호환성 비용 |
| 한 번 승격 후 유지 | 실행 중 위험·정체가 드러난 시점 | 반복 전환 억제, 어려운 후반부 대응 | 승격 판단 오류와 복구 시점 문제 |
| advisor | 주 모델이 필요할 때 다른 모델에 상담 | 주 실행 흐름 유지, 일부 판단만 강한 모델 사용 | 상담 필요를 감지해야 하고 추가 호출 발생 |
| 작업 분할 | 독립 하위 작업의 시작 | 작은 맥락·병렬 실행 활용 | 맥락 전달·결과 통합·조정 비용 |

단계별 재선택은 매 단계 모델을 바꾼다는 뜻이 아니다. ‘현재 모델 유지’가 정상 선택지다. 클라이언트 도구 루프에서는 도구 결과를 반영해 다음 모델 요청을 만들 때 개입할 수 있다. 서버 내부에서 수행하는 도구 루프에는 클라이언트가 매 단계 개입할 수 있다고 가정하지 않는다. [D04](../references/sources.md#d04), [D08](../references/sources.md#d08)

### 같은 구현에서 선택 주기를 바꾸는 사례

Switchyard Classifier는 `every_request`, `user_turn`, `new_session`을 제공한다. 특히 `user_turn`은 새 사용자 메시지 때 선택하고 이어지는 도구 요청에는 유지하므로 최초 질문의 두 선택지를 직접 비교할 수 있는 구현이다. Stage는 도구 진행 신호로 양방향 재선택, Escalation은 응답 평가 후 강한 모델로 고정하는 별도 정책이다. [R06](../references/sources.md#r06)

Weave는 action별 새 추천과 세션 pin을 캐시 경제성으로 비교하는 planner를 제공한다. 따라서 선택 주기와 실제 전환 주기는 별개의 설계 변수다. 다만 추천기는 학습 artifact에 의존하며, cache planner는 분리된 결정적 계산이다. [R07](../references/sources.md#r07)

## 캐시 관련 사실

프롬프트 캐시는 모델이 입력 prefix를 처리하며 만든 계산 상태를 재사용한다. 일반적인 이종 모델 API에서는 A의 KV 상태를 B가 그대로 재사용한다고 가정하지 않는다. 공통 prefix가 있어도 캐시의 존재·수명·라우팅 위치가 맞아야 실제 hit가 난다. [D01](../references/sources.md#d01)

- A→B 전환은 A의 캐시를 삭제하는 동작과 다르다.
- A→B→A에서 A의 기존 prefix가 유효하면 그 부분을 다시 사용할 수 있다. B 실행 중 늘어난 부분은 A가 처리해야 한다.
- B에서도 유효한 prefix 캐시가 이미 있거나 전환 후 쌓일 수 있다. 전환 비용을 남은 여러 단계에서 회수할 가능성이 있다.
- 시스템 지시문·도구 목록·과거 메시지·일부 생성 설정을 바꾸면 같은 모델에서도 캐시가 깨질 수 있다.
- 도구 정의를 기존 prefix 앞쪽에 매번 재구성하는 것과, 지원 API에서 뒤쪽에 추가하는 것은 캐시 효과가 다르다.
- 출력과 reasoning 토큰 비용은 프롬프트 캐시 할인으로 사라지지 않는다.

공식 동작: [OpenAI 캐시 D01](../references/sources.md#d01), [Claude thinking D03](../references/sources.md#d03), [Claude 도구 캐시 D08](../references/sources.md#d08).

Switchyard의 `theoretical_cache_hit_rate` 같은 prefix 재사용 가능성은 실제 제공자 cache-hit와 다르다. Weave는 이전 usage를 사용한 전환 비용 추정과 실행 후 비용 회계를 별도 코드로 관리한다. 이 둘을 각각 ‘추정·결정’과 ‘실측·평가’의 구현 예로 참고한다. [R06](../references/sources.md#r06), [R07](../references/sources.md#r07)

### 작은 계산 예시

실제 가격표가 아닌 가정: 이력 100,000토큰, A의 cache read가 $1/백만 토큰, B의 fresh input이 $2/백만 토큰이다. 기존 이력만 읽는다면 A 유지에 $0.10, 캐시 없는 B로 이동에 $0.20가 든다. 신규 입력·출력·별도 쓰기 비용은 제외했다.

이는 한 단계의 예시다. B의 이후 캐시 읽기·출력 단가·필요 단계 수에 따라 전체 결과가 역전될 수 있다. 전환 판단에는 남은 실행 비용을 비교해야 한다.

## 직접 관련된 에이전트 연구

### MTRouter

누적 이력과 모델 표현을 결합해 단계별 모델 효용을 추정하는 **학습된 라우터**다. ScienceWorld의 성공 실행 분석에서는 Router-R1보다 전환이 적었다(대략 5회 대 20회). 논문은 캐시 손실과 전환 지연을 한계로 명시한다. 따라서 ‘상태를 반영하면서 불필요한 전환을 억제한다’는 아이디어는 참고하되, 현재 무학습 구현의 직접 방법으로 채택하지 않는다. [P01](../references/sources.md#p01)

### TwinRouterBench

정적 prefix 평가와 실제 에이전트 실행 평가를 나눈다. 실제 실행에는 제공자 사용량·캐시 회계·API 비용을 반영한다. 100개의 held-out SWE-bench Verified 문제에서 보고한 값은 다음과 같다.

| 정책 | 해결 수 | 실제 API 비용 |
|---|---:|---:|
| Opus 4.6 고정 | 74/100 | $54.73 |
| 학습된 UncommonRoute | 75/100 | $25.66 |
| 규칙 기반 UncommonRoute | 73/100 | $172.56 |

학습된 정책의 API 비용 절감은 약 53.1%지만, 이 결과는 무학습 라우터의 성능 증거가 아니다. 규칙 기반 정책도 잘못 구성하면 고정 모델보다 비싸질 수 있다. 논문 leaderboard는 실패 건당 $0.60의 가상 패널티를 별도로 더하므로 실제 API 비용과 혼동하지 않는다. 특정 모델 풀과 100문제의 초기 결과다. [P02](../references/sources.md#p02)

### SWE-Router

저렴한 모델이 몇 단계 탐색한 이력으로 계속 실행할지 판단한다. 최초 질문만으로 난이도가 드러나지 않는 문제를 다룬다. 승격 때 강한 모델은 원래 질문에서 **재시작**하며, 값 함수는 학습된다. 이 결과를 ‘무학습 상태 인계가 검증됐다’고 읽으면 안 된다. [P03](../references/sources.md#p03)

### TACIT-Switch

반복 행동·진행 정체 등 누적 위험으로 한 번만 강한 모델에 넘기고 나머지 실행을 맡긴다. 정책은 오프라인 실행과 teacher annotation에서 학습한다. 비용은 모델 규모로 가중한 호출 수를 대리값으로 사용하므로 실제 캐시 청구액 최적성을 입증하지 않는다. 유지 정책의 비교 대상으로 참고한다. [P04](../references/sources.md#p04)

## 운영 사례와 추가 함정

2026-09-06 확인한 OpenRouter Auto Router는 작업 유형을 분류하고 최근 7일의 유형별 지출 점유율로 후보를 정렬한다. 각 단계에서 재평가하되, 기존 모델이 여전히 상위 후보이면 유지하는 세션 동작을 설명한다. 제공자 stickiness도 별도로 적용한다. **절대적인 작업 종료까지의 모델 고정은 아니다.** 검색 결과에 남은 예전 Not Diamond 기반·무조건 고정 설명보다 최신 페이지 본문을 기준으로 삼았다. 시장 지출은 모델의 성공률과 동일한 신호가 아니다. [D05](../references/sources.md#d05)

추가로 Augment Prism의 공식 설명은 **사용자 턴 시작에 planner로 선택하고, 해당 턴의 도구 후속 요청에서는 모델을 고정**하는 구조다. 다음 사용자 턴에는 예상 이득과 캐시 비용을 비교한다. OpenRouter의 조건부 유지와 구분되는 운영 사례이며, 어느 쪽도 모든 작업의 최적 정책을 입증한 것은 아니다. planner 학습 과정은 공개 본문만으로 확인하지 못했다. 업체가 쓰는 ‘cache eviction’을 이전 모델 캐시의 보편적인 물리 삭제로 해석하지 않는다. [D09](../references/sources.md#d09)

모델 전환은 메시지 전달만으로 끝나지 않는다. 도구 스키마, 호출·결과 ID, 추론 블록, 컨텍스트 한도, API 상태의 호환성도 필요하다. Claude는 대상 모델이 읽을 수 없는 이전 thinking 블록을 무시하거나 제거할 수 있다고 문서화한다. [D03](../references/sources.md#d03)

별도 advisor와 작업 분할도 후보지만, 긴 의존 관계가 있는 작업에 무조건 유리하지 않다. Anthropic 운영 가이드는 상담 빈도와 작업의 독립성을 측정하고 단일 모델의 낮은 effort 설정과 비교할 것을 권한다. [D02](../references/sources.md#d02)

모델을 유지하고 effort만 바꾸는 후보도 있다. 일부 API에서는 설정 변경이 prefix를 바꾸므로, 지원되는 경우 대화 뒤쪽에 configuration update를 추가하는 방식을 확인해야 한다. [D07](../references/sources.md#d07)
