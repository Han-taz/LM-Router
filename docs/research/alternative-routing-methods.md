# 추가 라우팅 방법론: 임베딩 검색을 넘어

확인일: 2026-09-06 · 상태: 문헌·공개 코드 조사, 자체 실험 없음 · [문서 안내](../README.md)

## 이 문서의 범위

후속 광범위 조사에서 RouteProfile·CASCAL·Pandora·DialRouter·bandit·effort·token-level까지 확장했다. 전체 분류는 [방법론 지도](literature-landscape.md), 신규성·개발 판단은 [별도 결론](novelty-and-feasibility.md)을 따른다. 이 문서는 아래 일곱 방법의 상세 설명을 유지한다.

Avengers/Avengers-Pro, Eagle, SkewRoute, PORT, VDAR 및 Switchyard·Weave는 [기존 방법 조사](training-free-methods.md)에 있다. 여기서는 그 밖의 방법을 **결정에 쓰는 증거, 필요한 사전 데이터, 온라인 추가 실행, 에이전트 적용 범위**로 비교한다. 논문에 training-free라고 적혀 있다는 이유만으로 현재 프로젝트 조건에 맞는다고 판단하지 않는다.

핵심 결론은 방법을 하나 고르는 것보다 다음 세 축을 분리해야 한다는 것이다.

| 설계 축 | 선택지 | 구분이 필요한 이유 |
|---|---|---|
| 무엇을 보고 고르는가 | 의미·유사 사례·자기 검증·확률·응답 일치·도구 결과 | 라벨·추론 호출·검증 가능성 요구가 다름 |
| 무엇을 고르는가 | 모델 / 직접 답변 대 agent / 재시도·상담 등 실행 방식 | 실행 방식 선택은 모델 교체보다 더 큰 비용·권한 차이를 만듦 |
| 언제 바꿀 수 있는가 | 사용자 턴 시작 / 각 모델 호출 / 실패·정체 때만 | 같은 판단기를 써도 캐시·지연·성공률이 달라짐 |

예를 들어 kNN은 모델 추천 방법이고, 턴 내 고정은 전환 정책이다. 서로 경쟁하는 단일 대안이 아니라 결합 가능한 별개 요소다. 아래 적용 판단과 실험 제안은 문헌을 종합한 **프로젝트 제안**이며 입증된 최적 정책이 아니다.

## 추가 방법 비교

아래의 ‘학습 없음’은 기존 범용 모델/임베딩의 사전학습까지 부정하는 뜻이 아니다. 정답 라벨 없음, 신경망 fine-tuning 없음, 정책 보정 없음도 서로 다르다.

| 방법·대표 자료 | 결정 신호 | 사전 준비 | 온라인 추가 비용 | 우선 검토 조건 |
|---|---|---|---|---|
| 정적 semantic 경로 — Aurelio | 사람이 정한 예시 문장과의 유사도 | 경로별 예시·수동 모델 매핑. 자동 보정은 선택 | 임베딩·검색 | 모델 성능 label 없이 시작하고 싶을 때 |
| 사례별 kNN — Rethinking Predictive Modeling | 가까운 개별 사례의 모델 성능·비용 | 모델별 평가 기록·색인 | 임베딩·검색 | 성능 데이터는 허용하지만 클러스터링도 피하고 싶을 때 |
| CP-Router | 작은 모델의 선택지 확률과 prediction-set 크기 | 정답이 있는 calibration·오류율 선택 | 작은 모델 확률 계산, 선택적 상위 호출 | 객관식/제한된 답 공간·logits 접근이 가능할 때 |
| CARGO | 작은 모델의 prompt별 답변 일치도 | 무라벨 warmup·offload 비율 보정 | 작은 모델 반복 생성, 선택적 상위 호출 | 로컬 생성이 저렴하고 답변 동등성 판정이 쉬울 때 |
| Smoothie / Smoothie-Train | 여러 모델 출력 임베딩의 관계 | 기본형: 현재 출력들 / Train: 별도 무라벨 질의의 출력 기록 | 기본형은 후보 모두 생성 / Train은 검색 후 선택 | 정답은 없지만 후보들의 출력 수집은 가능할 때 |
| BoundaryRouter | 비슷한 질의에서 LLM·agent의 출력/지연 + rubric | 양쪽 실행의 무라벨 경험 memory | 검색 + 기존 LLM 판단 | 모델보다 ‘agent 실행이 필요한가’를 고를 때 |
| AutoMix | 작은 모델 답변의 context-grounded 자기 검증 | few-shot 예시; POMDP형은 성능 데이터·KDE 추정 | 작은 모델 생성·복수 검증·선택적 승격 | 자기 검증 cascade의 고전적 비교 대상으로 |

출처: [R08](../references/sources.md#r08), [P11](../references/sources.md#p11), [P12](../references/sources.md#p12), [P13](../references/sources.md#p13), [P14](../references/sources.md#p14), [P15](../references/sources.md#p15), [P16](../references/sources.md#p16).

## 1. 사람이 정한 semantic 경로

**Aurelio Semantic Router**는 `Route`마다 예시 발화들을 정의하고, 입력 임베딩과 가까운 경로를 찾는다. 기본 정적 경로에서는 생성형 LLM이 답변을 쓰면서 판단할 필요가 없다. 예시·threshold를 수동으로 정하면 별도 신경망 라우터 fitting도 필수가 아니다. [R08](../references/sources.md#r08)

Avengers와의 차이는 **예시가 어떤 모델에서 성공했는지 자동 평가한 성능표 없이도 경로를 만들 수 있다**는 것이다. 대신 ‘이 유형은 이 모델에 보내도 충분하다’는 가정은 개발자가 책임진다. 엄밀한 data-free라기보다는 사람이 만든 예시를 사용하는 방법이다.

- 장점: 시작이 단순하고, 선택에 영향을 준 예시를 확인하기 쉽다. 경로를 모델 ID 대신 작업 유형에 연결해 카탈로그와 분리할 수 있다.
- 단점: ‘코딩’이라는 주제는 알아도 단순 문법 설명과 어려운 장애 분석을 구분한다는 보장은 없다. 부정·지시어·한국어 표현·장문에 대한 검증이 필요하다.
- 코드 경계: `SemanticRouter`는 색인 검색과 경로 점수화를 제공한다. `BaseRouter.fit`는 labeled route 데이터로 임계값을 최적화하는 별도 기능이다. 정적 경로, threshold fitting, LLM을 부르는 dynamic route를 섞어 ‘모두 무학습·무호출’이라고 설명하지 않는다.
- 적용 제안: 최종 품질 예측기보다 **작업 유형 후보 생성** 또는 기능 필터의 보조 신호로 먼저 평가한다. 매칭이 없을 때의 유지/보수적 fallback은 별도 정책으로 둔다.

## 2. 클러스터 대신 개별 사례를 찾는 kNN

**Rethinking Predictive Modeling for LLM Routing**은 입력과 가까운 k개 사례에서 모델별 성능과 비용을 평균하여 효용을 예측하는 비모수 방법을 비교한다. [P11](../references/sources.md#p11)

```text
Avengers-Pro: 질의 → 가까운 클러스터 → 클러스터별 모델 성능·비용표
kNN utility:  질의 → 가까운 개별 사례 k개 → 사례별 모델 성능·비용 집계
```

- 장점: 클러스터 fitting 없이 개별 사례를 활용한다. 어떤 사례를 근거로 선택했는지 추적하기 쉽다. 성능과 비용 추정을 분리하면 가격 변경을 다루기도 쉽다.
- 단점: 성능 label은 여전히 필요하다. k·거리·이웃 품질·대표성에 민감하고 저장·검색 비용이 있다. 새로운 모델을 추가할 때 평가 기록도 확보해야 한다.
- 결과 해석: 논문은 kNN이 복잡한 방법과 경쟁적임을 보였지만 항상 1등이라는 뜻은 아니다. 확인한 표의 텍스트 평균 AUC는 kNN(k=100) 52.68, Linear 53.14다. 이 수치를 에이전트 성공률로 읽으면 안 된다.
- 공개 구현 주의: [ULab LLMRouter의 KNNRouter](../references/sources.md#r09)는 현재 질의별 최고 **성능** 모델을 label로 만들고 `KNeighborsClassifier`로 투표한다. 위 논문의 성능·비용 utility 예측기와 동일한 구현이 아니다. `trainer.py`의 `.fit`는 이웃 분류기의 데이터 준비이지 신경망 gradient 학습은 아니지만, label 의존성은 남는다.

**적용 제안:** 데이터 허용 시 Avengers-Pro와 같은 support set·임베딩·입력 맥락·후보 풀로 비교할 가장 직접적인 추가 기준선이다. 모델별 전체 작업 성과를 쓸지 단일 응답 성과를 쓸지도 동일하게 맞춘다. kNN 추천 뒤의 캐시 유지 판단은 별도다.

## 3. 확률·불확실성으로 선택하는 CP-Router

**CP-Router**는 작은 일반 LLM과 reasoning model 등을 고른다. 작은 모델의 답 선택지 logits로 확률을 구하고, conformal prediction으로 만든 ‘가능한 정답 집합’이 하나이면 작은 모델을 사용하고 여러 개이면 더 강한 쪽으로 보낸다. [P12](../references/sources.md#p12)

여기서 추가 신경망 학습은 없지만 **정답이 있는 calibration set**이 필요하다. FBE라는 기준으로 prediction-set 크기 분포를 살펴 오류율 α를 고르는 보정도 있다. 확인한 v1은 test 입력의 집합 분포로 α를 탐색한다고 명시한다. 이는 test 정답을 사용한다고 명시한 것과는 다르지만, 고정 정책의 독립 평가와도 다르므로 우리 실험에서는 별도 개발/보정/평가 분리를 우선한다.

- 장점: 모델에게 막연히 “얼마나 자신 있어?”라고 묻는 것보다 불확실성을 명시적으로 다룬다.
- 제약: 답 선택지 확률에 접근해야 한다. 임의의 장문·도구 계획에는 바로 적용되지 않는다. open-ended QA 실험도 작은 모델이 답 후보 4개와 Others를 구성해 객관식으로 바꾸는 절차를 사용한다.
- 보장 범위: 가정 하의 **prediction-set marginal coverage**가 모든 요청의 정확도, 작은 모델로 보내진 부분집합의 정확도, 전체 agent 성공률을 자동 보장하지 않는다. 데이터 이동·adaptive α 선택도 별도 검토 대상이다.
- 비용: 논문의 출력 토큰 절감 지표와 실제 입력·캐시·선행 확률 계산 비용은 다르다.

**적용 제안:** 일반 agent의 1차 선택기보다는 답 공간이 제한된 하위 작업에서 비교할 후보다. 도구 API 실패·문맥 누락이 원인인 경우 불확실성 하나로 해결되지 않는다.

## 4. 반복 답변의 일치도를 쓰는 CARGO

**CARGO**는 작은 모델에 의미를 유지한 여러 system prompt를 주고 deterministic decoding으로 생성한다. 응답별 일치도를 Beta 분포로 추정하고, 그 추정의 불확실성이 충분히 줄면 샘플링을 끝낸다. 이후 일치도를 cloud offloading 확률로 바꾼다. 목표 cloud 호출 비율에 맞춘 λ는 무라벨 warmup 질의로 보정한 뒤 고정한다. [P13](../references/sources.md#p13)

- 장점: 별도 정답 label이나 신경망 분류기 대신 현재 모델의 실제 반응을 관측한다. logits가 없어도 최종 답 비교가 가능한 작업에서 사용할 수 있다.
- 단점: 일관되게 틀리는 모델도 있다. 높은 일치도는 높은 정답 확률과 같은 말이 아니다. 자유 서술·서로 다른 유효한 코드·도구 계획에서는 ‘같은 답’의 정의부터 필요하다.
- 비용 함정: 작은 모델 여러 번 + 필요한 경우 cloud 호출이다. 로컬 계산이 저렴한 설정의 장점을 여러 유료 API 호출 설정으로 그대로 옮길 수 없다. cloud 호출 비율이나 cloud 토큰 예산을 맞춘 실험은 총비용을 맞춘 실험과 다르다.
- 캐시 함정: system prompt를 앞부분부터 바꾸면 공통 prefix 재사용에 불리할 수 있다. 이는 원문의 변형 위치와 캐시 원리를 종합한 적용상 추론이며, 해당 논문이 관리형 API cache 비용을 검증했다는 뜻은 아니다.
- agent 제약: 답변 후보를 생성하는 것과 도구를 실제 반복 실행하는 것을 구분한다. 파일 변경·메일 발송 등 부작용이 있는 실행을 일치도 측정용으로 중복 수행하지 않는다.

**적용 제안:** 짧고 검증 가능한 답, 아주 저렴한 로컬 모델이 있는 경우에 한정해 먼저 비교한다. 모든 도구 단계에서 반복 샘플링하는 기본 정책으로 채택할 근거는 부족하다.

## 5. 정답 라벨 대신 여러 모델의 출력으로 추정하는 Smoothie

**Smoothie**는 여러 후보의 출력 임베딩 사이 거리를 이용해 잠재적인 정답 임베딩과의 품질 관계를 추정한다. triplet 기반 closed-form 계산이므로 SGD는 없지만 통계적 품질 가중치 추정은 존재한다. [P14](../references/sources.md#p14)

두 버전을 구분해야 한다.

| 버전 | 선택에 쓰는 출력 | 현재 요청의 여러 후보 생성 필요 | 우리 관심사와의 관계 |
|---|---|---|---|
| Smoothie-Global/Local 기본형 | test 질의들에 대한 여러 모델 출력 | 필요 | 응답 선택·품질 추정 연구. 저비용 사전 선택기와 다름 |
| Smoothie-Train 변형 | 별도의 무라벨 질의들에 대해 미리 만든 출력 | 선택 자체에는 불필요 | 유사 과거 사례로 먼저 모델을 고를 수 있음 |

**중요:** ‘라벨이 없으니 준비 비용도 없다’가 아니다. Train 변형도 사전 질의를 여러 후보 모델에 실행해야 한다. 기본 triplet 추정에는 최소 세 출력 제공자의 관계가 필요하므로, 모델 2개만 두는 설정에 수식 그대로 적용할 수 없다.

- 장점: 사람의 정답·선호 label을 얻기 어려운 생성 작업에서 참고할 수 있다.
- 한계: 모델들의 오류 독립성 가정이 현실에서 어긋날 수 있다. 공유된 오답·표현상 유사성이 품질처럼 보일 위험이 있다. 원문은 모델 가격을 목적 함수에 넣지 않는다고 명시한다.
- 코드 경계: `src/model.py`의 `.fit`는 거리와 triplet 수식을 계산한다. `run_smoothie.py`는 `train_time`/`test_time`을 구분하지만 사전 생성 파일에서 test 답변을 고르는 평가 runner다. 그대로 production gateway로 사용할 수 있는 코드라고 소개하지 않는다.

**적용 제안:** 성능 label은 배제하지만 무라벨 출력 수집은 허용한다면, **Smoothie-Train + 별도 가격·캐시 판단**을 연구 후보로 둔다. 이 결합의 비용·성능 개선은 우리가 검증해야 하는 가설이다.

## 6. 모델이 아니라 직접 답변과 agent 실행을 고르는 BoundaryRouter

**BoundaryRouter**는 가벼운 직접 LLM 답변과 전체 agent 실행 중 하나를 고른다. 소수 seed 질의를 양쪽에서 실행하고 질문·출력·지연만 저장한다. 새 질의에서는 비슷한 사례를 sparse+dense 검색으로 찾고 기존 LLM이 rubric을 적용해 선택한다. memory에 정답·정오 label·reward를 넣지 않는다. [P15](../references/sources.md#p15)

- 장점: ‘어떤 모델인가’보다 앞서 **도구와 여러 단계 실행이 필요한가**를 판단해 더 큰 비용 차이를 다룬다. label 없이 관측 가능한 경험을 활용한다.
- 단점: 초기 양쪽 실행 비용, 검색, 별도 routing LLM 호출이 필요하다. 모델 judge가 출력의 그럴듯함과 실제 정확성을 혼동할 수 있다.
- 범위: agent 내부에서 매 단계 모델을 바꾸는 논문이 아니다. 현재 agent가 이미 시작된 뒤 direct LLM으로 바꾸는 동작이 검증됐다는 뜻도 아니다.
- 권한·기능: 사용자가 실제 파일 수정·최신 검색 등 도구가 필요한 결과를 요청했다면, 싸다는 이유로 일반 답변으로 대체해서는 안 된다. 직접 답변이 과업 요구를 충족할 수 있을 때만 후보로 둔다.
- 코드 상태: 확인한 원문은 향후 코드·데이터 공개를 언급한다. 이번 조사에서는 공식 실행 저장소를 확인하지 못했다.

**적용 제안:** ‘같은 agent의 executor 모델 선택’이 먼저인 현재 프로젝트에서는 범위 확장 후보로 보관한다. 처음부터 모델·실행 방식·전환 주기를 동시에 바꾸면 효과의 원인을 구분하기 어렵다.

## 7. 자기 검증 cascade의 대표: AutoMix

**AutoMix**는 작은 모델의 답변을 같은 모델이 few-shot entailment 방식으로 검증하고, 판정 비율에 따라 상위 모델로 넘기는 흐름을 제시한다. 간단한 threshold 버전과 POMDP 버전을 구분한다. [P16](../references/sources.md#p16)

- verifier는 추가 fine-tuning하지 않는다. 그러나 복수 검증 호출을 한다.
- POMDP 버전은 train set에서 관측 분포를 KDE로 추정하고 계획 solver를 사용한다. ‘별도 neural router가 없다’와 ‘정책 fitting도 없다’는 다르다.
- 작은 모델의 자기 검증을 실제 테스트·정답 검사와 동일시하지 않는다. 문제에 답할 근거 자체가 없으면 더 큰 모델을 호출해도 해결되지 않을 수 있다.

**적용 제안:** 우리 조건에 직접 맞는 최소형은 ‘관측 가능한 테스트·스키마·정답 검사 + 수동 승격 정책’이다. 이것은 AutoMix 전체 알고리즘의 재현이 아니라 [기존 검증 기반 후보](training-free-methods.md)의 별도 구현안이다. 검증 결과가 나기 전 답변 streaming을 보류해야 하는지, 이미 실행된 도구 행동을 어떻게 다룰지도 필요하다.

## 실제 운영 구조 참고: Augment Prism

새로 확인한 **Augment Prism** 공식 설명은 이번 캐시 문제와 직접 관련된다. 작은 planner가 **사용자 턴 시작**에 선택하고, 같은 턴의 tool-result 후속 요청은 그 결정을 재사용한다. 다음 사용자 턴에는 새 모델의 예상 이득과 캐시 전환 비용을 비교한다. [D09](../references/sources.md#d09)

이는 ‘도구를 호출할 때마다 꼭 다시 라우팅해야 한다’의 반례가 되는 운영 사례다. 다만 planner가 어떻게 학습됐는지는 공개 설명으로 확정하지 못했으므로, **무학습 알고리즘의 증거가 아니라 선택 주기·캐시 정책의 참고**다.

업체 글은 추가 판단 호출의 돈과 지연을 따로 보고한다. 공개 traffic 설명에서 planner 중앙 지연은 약 2.6초이며, 호출되는 새 사용자 턴에서는 체감 지연의 상당 부분을 차지한다. 전체 도구 후속 요청에 나누면 평균 overhead가 작아 보여도 사용자가 새 질문을 보냈을 때의 대기는 클 수 있다. 따라서 우리도 ‘모든 모델 요청 평균’과 ‘새 사용자 턴의 time-to-first-token’을 따로 측정해야 한다.

주의할 표현: 업체가 말하는 cache eviction을 모든 API에서 이전 모델 캐시가 물리적으로 삭제된다는 뜻으로 일반화하지 않는다. A→B→A의 재사용 조건은 [캐시 문서](agent-routing-and-cache.md)를 따른다. 업체 benchmark·운영 수치는 독립 검증하지 않았다.

## 우리 프로젝트의 조사·실험 우선순위 제안

1. **공통 운영 기준선:** 기존 규칙·진행 신호에 사용자 턴 내 유지와 단계별 재평가를 각각 붙여 비교한다. 기능 충족·맥락 전달·총비용 회계는 동일하게 둔다. 선택기가 달라져도 유지·전환 정책은 독립 비교한다.
2. **모델별 평가 데이터 허용:** Avengers-Pro와 **kNN utility**를 같은 데이터로 비교한다. 이웃 검색으로 충분한데 클러스터 또는 판단 LLM이 꼭 필요한지부터 확인한다.
3. **성능 label 금지, 무라벨 출력 수집 허용:** **Smoothie-Train**을 후보로 둔다. 과거 출력 수집까지 배제한다면 정적 semantic 경로·수동 규칙·선택적 기존 LLM 판단이 더 직접적인 시작점이다.
4. **저가 실행 후 판단 가능:** 먼저 객관적 verifier 기반 승격을 비교한다. 확률 접근·답 형식·단가 조건이 맞을 때만 CP-Router/CARGO를 추가한다.
5. **실행 방식까지 연구할 때:** BoundaryRouter형 direct/agent 선택을 모델 선택과 별도 실험으로 확장한다.

새로 필요한 진단은 ‘성능표/출력 memory 구축 비용’, ‘반복 샘플 수’, ‘검증 뒤 잘못 수락한 비율’, ‘캐시 전환 후 실제 비용’, ‘새 사용자 턴의 판단 지연’이다. 자세한 실험 분리는 [평가 계획](../evaluation/experiment-plan.md)에 연결한다.

**현재 판단:** ‘완전 무학습 라우터 중 최고’를 지금 정할 근거는 부족하다. 먼저 **허용하는 준비 데이터와 추가 호출**을 명시하고, 동일한 대화 입력·agent harness·캐시 조건에서 비교하는 것이 이 프로젝트에 더 중요한 다음 단계다.
