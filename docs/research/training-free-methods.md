# 학습 없는 라우팅 방법 조사

확인일: 2026-09-06 · 상태: 방법 비교 · [문서 안내](../README.md)

## ‘학습 없음’의 구분

이 프로젝트는 라우터를 별도로 학습하지 않는 방향이다. 하지만 논문 제목의 training-free는 데이터·최적화·추론 비용이 없다는 뜻이 아닐 수 있다.

| 분류 | 방식 | 필요한 것 | 현재 취급 |
|---|---|---|---|
| A | 수동 규칙·기능 필터·가격 계산 | 설정·모델 명세 | 우선 후보 |
| B | 기존 범용 LLM에 rubric을 주어 선택 | 사전학습된 범용 모델의 추론 호출 | 추가 라우터 호출을 허용할 경우 후보 |
| C | frozen embedding + 과거 사례 검색·순위표 | 과거 모델별 성능/선호도·임베딩 | 무가중치학습이지만 데이터 의존. 별도 후보 |
| D | 초기 데이터로 임계값·최적화 변수 추정 | calibration/development 데이터·최적화 | 신경망 학습이 없어도 정책 fitting이 존재. 별도 표시 |
| E | 남이 학습한 전용 라우터 사용 | 학습된 전용 체크포인트·서비스 | ‘내가 학습하지 않음’에 해당. 순수 무학습의 증거로 쓰지 않음 |
| F | supervised/RL/bandit로 정책 갱신 | 정답·보상·학습 과정 | 현재 구현 방향에서 제외 |

기존 범용 LLM·임베딩 모델 자체가 사전학습됐다는 사실과, 이 프로젝트가 라우터를 추가 학습하는 것은 구분한다. 반대로 온라인 성능 집계로 선택 정책을 자동 갱신하면 gradient가 없어도 적응형 정책이다.

## 바로 구성할 수 있는 후보

### 후보 1. 기능 필터 + 수동 규칙 + 비용 비교

요청에 필요한 도구·이미지·컨텍스트·출력 형식을 지원하지 않는 모델을 제거한다. 남은 모델에 대해 작업 유형, 검증 가능성, 진행 정체, 캐시 추정, 비용 한도를 규칙으로 적용한다.

- 장점: 결정이 재현 가능하고 설명하기 쉽다. 라우터용 모델 API 호출이 없다.
- 한계: 키워드·길이는 난이도의 대리 신호다. 짧은 어려운 질문, 한국어 표현, 도구 실행 중 나타난 복잡성에서 틀릴 수 있다.
- 참고: router-core의 분류→필터→순위 구조, LiteLLM의 기본 complexity scorer, Portkey의 조건 엔진. [R01](../references/sources.md#r01), [R03](../references/sources.md#r03), [R04](../references/sources.md#r04)
- 프로젝트 제안: 하나의 복잡도 점수로 모든 것을 결정하지 말고, 기능 제약·작업 역할·캐시·운영 상태를 분리한다.

### 후보 2. 기존 LLM을 사용하는 rubric 기반 라우터

범용 LLM에 현재 작업, 필요한 기능, 최근 진행 상태, 후보의 명세를 주고 제한된 스키마로 선택 근거를 받는다. 별도 가중치 학습은 없다. LangChain은 모델 호출 미들웨어를 통해 이런 정책을 삽입할 수 있는 위치를 제공한다. 이 자체의 성능은 별도 평가해야 한다. [D04](../references/sources.md#d04)

- 장점: 수동 키워드 규칙이 놓치는 의미·상태를 해석할 수 있다.
- 비용: 라우터의 입력·출력·지연·오류도 전체 비용에 포함한다. 매 단계 전체 이력을 다시 읽히는 설계는 특히 비쌀 수 있다.
- 프로젝트 제안: 판단용 모델에는 필요한 요약 상태를 주되, 요약 생성 비용과 정보 손실을 측정한다. 모델 ID·요금·지원 기능은 코드가 검증한다.
- 한계: 모델이 말한 confidence를 검증 없이 확률로 해석하지 않는다. 반환 JSON 오류·알 수 없는 모델 선택에 대한 결정적 fallback이 필요하다.

### 후보 3. 저가 모델 실행 + 검증 + 제한적 승격

테스트·스키마·정답 검사로 실패를 판별할 수 있는 작업에서 저가 모델을 먼저 시도한다. 검사 실패 또는 진행 정체가 지속될 때 상위 모델을 선택한다.

이 패턴 자체는 학습 없이 구현할 수 있다. 다만 앞선 연구의 TACIT-Switch나 SWE-Router는 전환 정책을 학습하므로 동일한 방법이라고 부르지 않는다. [P03](../references/sources.md#p03), [P04](../references/sources.md#p04)

- 장점: 추상적 난이도보다 관측 가능한 결과로 판단한다.
- 한계: 최초 잘못된 행동이 복구 불가능하거나, 실행 결과를 검증할 수 없거나, 저가 모델의 시도 자체가 비싸면 부적합하다.
- 프로젝트 제안: 승격·재시작·현재 상태 인계를 다른 행동으로 기록한다. 도구 서버의 일시 장애를 모델 역량 부족으로 취급하지 않는다.

## 추가 공개 구현에서 확인한 경계

- **Switchyard Stage:** judge를 생략하면 도구 오류·진행 신호를 고정 규칙으로 처리한다. 추가 라우터 학습·판단 LLM 호출이 없는 직접 후보다. 다만 권장 임계값은 저자 데이터로 보정됐고, 코딩 도구의 읽기·쓰기·테스트 신호에 특화되어 있다. [R06](../references/sources.md#r06)
- **Switchyard Capability·Escalation:** 기존 LLM의 판단을 사용하므로 위 분류 B에 해당한다. 특히 응답 생성 후 검증하는 Escalation은 버려지는 저가 응답의 비용까지 발생한다. [R06](../references/sources.md#r06)
- **Weave cluster·HMM:** 학습된 centroid·품질표 또는 frozen PCA/HMM/XGBoost에 의존한다. ‘우리가 재학습하지 않고 사용’하는 후보와 ‘전용 라우터 학습을 배제’하는 후보를 구분해야 한다. [R07](../references/sources.md#r07)
- **Weave cache planner:** 위 추천기와 별도인 결정적 비용 계산이다. 학습된 추천기를 채택하지 않아도 모델 유지·전환 경제성의 설계 원리는 참고할 수 있다. 코드 도입은 라이선스 검토와 별개다. [R07](../references/sources.md#r07)

## training-free 논문에서 참고할 방법

### The Avengers와 Avengers-Pro: 임베딩·클러스터·성능표

사용자가 기억한 ‘임베딩만으로 라우팅하는 어벤져스’에 해당하는 유력한 논문 계열이다. 두 논문은 **온라인 선택에 생성형 LLM judge가 필요하지 않다**는 점에서 직접 관련되지만, 임베딩만으로 모델 능력을 알아내는 것은 아니다.

| 논문 | 발표 | 핵심 차이 |
|---|---|---|
| The Avengers | 2025-05, 확인 v3 | 최근접 클러스터의 우수 모델 선택 + 반복 샘플링·투표로 성능 향상 |
| Avengers-Pro | 2025-08, 확인 v2 | 가까운 여러 클러스터에서 성능·비용을 함께 평가해 모델 선택 |

공통 구조는 오프라인 준비와 온라인 선택으로 나뉜다.

1. **오프라인:** 정답·평가가 있는 질의를 임베딩하고 클러스터를 만든다. 후보 모델들의 해당 질의 성과를 평가해 클러스터별 모델 성능표를 만든다. Pro는 비용 정보도 사용한다.
2. **온라인:** 새 질의를 같은 임베딩 모델로 변환하고 가까운 클러스터를 찾는다. 미리 만든 모델 점수표를 조회해 모델을 선택한다. 그 뒤 선택된 모델이 실제 답변을 생성한다.

따라서 추가 신경망 라우터 fine-tuning과 생성형 LLM 판단은 필수가 아니지만, clustering fitting과 모델별 성능 데이터는 필요하다. 원 논문도 이를 offline calibration이라 부른다. 원형은 반복 생성·투표까지 포함하므로 전체 시스템이 임베딩 한 번 비용으로 끝나는 것은 아니다. [P09](../references/sources.md#p09)

Pro 논문의 3절 점수는 다음과 같다. 정확도와 비용을 클러스터 내 모델들 사이에서 각각 min-max 정규화한 뒤 사용한다.

```text
cluster_score(model) = α × normalized_accuracy
                     + (1 − α) × (1 − normalized_cost)

최종 모델 점수 = 가까운 top-p 클러스터의 cluster_score 합
```

α가 높으면 성능, 낮으면 비용을 더 중시한다. 논문 실험은 데이터를 70% 준비·30% 평가로 나누며, 공개 코드에도 KMeans `fit_predict`와 클러스터별 순위표 구축 단계가 있다. ‘test-time routing’이 사전 데이터 준비가 없다는 뜻은 아니다. 논문 설명과 현재 공개 코드의 세부 기본값은 동일하다고 가정하지 않는다. [P10](../references/sources.md#p10)

**프로젝트 적용 판단:** ‘라우터를 학습하지 않는다’가 **신경망 라우터의 가중치를 추가 학습하지 않는다**는 뜻이면 유력한 비교 후보다. 과거 모델 성능 수집·클러스터 fitting까지 배제한다면 원형 그대로는 조건에 맞지 않는다. 위 분류 C/D의 데이터 의존 후보로 두며, HMM·XGBoost 등의 전용 분류기를 불러오는 것과도 구분한다.

**맥락·캐시 한계:** ‘이건 어떻게 해?’만 임베딩하면 누락된 선행사 정보가 새로 생기지 않는다. 대화 맥락을 어떤 텍스트로 만들지 먼저 정해야 한다. 과거 클러스터를 단일 질의로 만들었는데 온라인에는 긴 대화 요약을 넣으면 입력 분포가 달라지므로 검증이 필요하다. 모델 추천 뒤에 캐시 유지·전환 정책을 붙이는 것은 별도 설계다. [입력 맥락](../design/router-input-and-context.md), [유지·전환 후보](../design/router-options.md)

Weave README는 Avengers-Pro에서 유래한 scorer라고 설명한다. 그러나 Weave의 현재 artifact·운영 정책은 원 논문과 동일한 알고리즘·설정이라고 가정하지 않는다. [R07](../references/sources.md#r07)

### Eagle: 지역·전체 Elo 순위

질의와 유사한 영역의 모델 능력과 전반적인 모델 능력을 Elo 방식으로 결합한다. 가중치 학습을 피하지만 과거 모델 비교·선호도 기록을 사용한다. 즉 데이터 없이 바로 최적 모델을 아는 방식이 아니다. 모델별 능력이 작업군에 따라 다르다는 표현 방식을 참고할 수 있다. 에이전트의 캐시 전환 최적화는 별도 문제다. [P05](../references/sources.md#p05)

### SkewRoute: 검색 결과의 점수 분포

KG-RAG의 검색 점수 분포를 이용한다. 관련 점수가 소수 결과에 집중되는지, 여러 결과에 퍼져 있는지를 누적합·엔트로피·Gini 등의 규칙으로 판별해 작은/큰 모델을 선택한다. 기존 검색기가 이미 만든 신호를 재사용하는 방식이다.

현재 프로젝트에 대한 의미는 ‘쿼리 텍스트뿐 아니라 도구가 만든 수치 신호도 라우팅에 활용할 수 있다’는 것이다. 특정 KG-RAG 검색 점수의 특성을 일반 코딩·브라우저 에이전트 난이도에 그대로 적용하면 안 된다. 임계값 선택과 기반 검색기의 학습 여부도 기록해야 한다. [P06](../references/sources.md#p06)

### PORT: 예산 제약 하 온라인 최적화

과거 데이터에서 근사 최근접 이웃으로 질의별 성능·비용을 추정하고, 초기에 관측한 소수 질의로 최적화 변수를 정한다. 논문은 모델 학습이 없다는 의미에서 training-free라 부르지만, 데이터와 초기 최적화가 필요하다.

전체 트래픽의 모델별 토큰 예산을 배분하는 문제에 적합한 근거다. 한 에이전트 작업의 모델 전환·캐시 상태를 직접 푼 것으로 해석하지 않는다. 현재의 수동 규칙 후보와 분리해 보관한다. [P07](../references/sources.md#p07)

### VDAR-Router: 난이도 분석 후 유사 사례 검색

기존 LLM이 질의의 난이도를 분석하고, 그 분석과 유사한 과거 사례를 검색해 후보의 성능·비용을 추정한다. 별도 라우터 가중치 학습 없이 동작하지만 과거 성능/선호도 데이터, 임베딩, 판단용 LLM 호출이 필요하다.

표면적인 문장 유사도와 실제 필요한 능력의 차이를 다룬다는 점이 유용하다. 오프라인 분석 데이터 구축 비용과 온라인 라우터 비용을 포함해야 한다. 에이전트 전체 실행·캐시 포함 절감의 증거로 바로 사용할 수는 없다. [P08](../references/sources.md#p08)

## 다른 방법론으로 확장

[추가 방법론 비교](alternative-routing-methods.md)에 다음 계열을 별도로 정리했다. 기존 논문 메모와 새 후보를 뒤섞지 않고, 준비 데이터·온라인 비용·에이전트 적용 범위를 같은 기준으로 비교한다.

- **사전 선택:** 사람이 정한 semantic 예시 경로, 클러스터 대신 개별 사례를 쓰는 kNN utility.
- **모델의 현재 반응 활용:** CP-Router의 확률·prediction set, CARGO의 반복 답변 일치, AutoMix의 자기 검증 cascade.
- **정답 label 없이 경험 활용:** Smoothie/Smoothie-Train의 출력 관계, BoundaryRouter의 LLM 대 agent 실행 선택.
- **선택 주기·캐시 운영:** Augment Prism의 사용자 턴 시작 선택과 턴 내 도구 후속 요청 고정. planner의 학습 여부는 공개 설명만으로 미확정.

‘모델 추천 알고리즘’과 ‘현재 모델을 유지할지 결정하는 전환 정책’은 분리한다. 또한 코드에 `.fit`가 있다는 사실만으로 neural training이라고 단정하지 않지만, 비신경망 방법의 데이터 fitting도 없던 것으로 취급하지 않는다.

## 흔한 오해

- training-free와 data-free는 다르다.
- 기존에 학습된 전용 라우터를 가져와 실행하는 것은 전용 라우터 학습이 없었던 것과 다르다.
- 규칙 임계값을 평가 데이터에 맞추고 같은 데이터로 보고하면 학습 여부와 무관하게 과적합된 평가다.
- semantic similarity가 비슷하다고 같은 모델이 충분한 것은 아니다.
- 모델 가격이 낮다고 성공 1건당 비용이 낮은 것은 아니다.
- 입력 길이와 필요한 추론 난이도는 별개다. 긴 단순 추출과 짧은 어려운 추론을 구분해야 한다.

## 이 프로젝트에서의 우선순위

우선 수동 규칙 기준선과 검증 결과에 따른 승격을 비교한다. 구체적인 에이전트 규칙은 Switchyard Stage, 별도의 유지·전환 경제성은 Weave planner를 우선 조사 대상으로 삼는다. 기존 LLM 판단은 추가 후보로 둔다. **임베딩 기반 후보는 Avengers-Pro를 먼저 읽되**, Eagle·PORT·VDAR 및 사전학습된 Weave 추천기와 함께 데이터 의존성의 허용 범위를 구분해 검토한다. 이 우선순위는 제안이며 사용자와 확정한 최종 아키텍처가 아니다.

추가 조사에 따른 보강: 평가 데이터를 허용한다면 Avengers-Pro의 직접 비교군으로 **kNN utility**를 포함한다. label은 금지하되 과거 출력 수집을 허용한다면 **Smoothie-Train**을 별도 후보로 둔다. CP-Router·CARGO·BoundaryRouter는 적용 조건과 과업 범위가 맞을 때 검토하며, 무조건 초기 구현 범위에 넣지 않는다.
