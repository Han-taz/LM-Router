# 학습 없는 라우터의 평가 계획

기준일: 2026-09-06 · 상태: **미실행 계획** · [문서 안내](../README.md)

## 검증할 가설

H1. 필수 기능을 먼저 검사하는 수동 규칙 라우터가, 고성능 모델 고정보다 비용을 줄이면서 허용 성공률 범위를 유지한다.

H2. 동일한 규칙에서 캐시와 유지 정책을 추가하면, 매 단계 독립 선택보다 실제 작업 비용·지연이 개선된다.

H3. 기존 범용 LLM을 애매한 경우에만 호출하면, 항상 LLM을 라우터로 쓰는 것보다 판단 비용을 줄이면서 유용한 적응성을 얻는다. 이 후보는 추가 라우터 LLM 호출을 연구 범위에 포함할 때만 평가한다.

가설은 결과가 아니다. 비용 절감 목표·허용 성공률 저하·평가할 작업군은 실행 전 확정한다.

후속 조사에서 H4(잔여 길이 불확실성·모델별 캐시), H5(판정과 전환의 공동 결정), H6(도구 상태 조건부 검색)를 추가 후보로 정리했다. 정의·선행연구·반증 기준은 [신규성 판단](../research/novelty-and-feasibility.md)에 있다. 한 번에 전부 구현하지 않고 H4를 우선 검토한다.

## 비교군

| ID | 정책 | 목적 |
|---|---|---|
| B0 | 고성능 모델 고정, 캐시 활성화 | 품질·비용 기준선. 항상 정답이라는 의미는 아님 |
| B1 | 저렴한 모델 고정, 캐시 활성화 | 라우팅 없이 얻는 절감과 실패율 파악 |
| B2 | 최초 요청의 규칙 점수로 모델 선택 후 작업 중 유지 | 요청별 라우팅 효과 |
| B3 | 같은 규칙으로 매 단계 재선택 | 실행 상태 활용 효과와 전환 비용 |
| B4 | B3 + 캐시 비용 추정 + 유지·전환 제한 | 캐시 인식 정책의 증분 효과 |
| B5 | B4 + 애매한 경우에만 기존 LLM 판단 | 추가 학습 없이 LLM 판단을 쓸 가치. 선택 실험 |
| B6 | 같은 판단용 LLM을 매 단계 호출, 동일한 기능·캐시·유지 제약 적용 | B5와 비교해 선택적 호출의 효과 검증. H3 평가 시 포함 |

같은 모델의 reasoning effort만 바꾸는 비교는 공급자가 지원한다면 포함한다. 이종 모델 전환이 단일 모델 계산량 조절보다 나은지 확인해야 한다. Ares 원문은 학습형이므로, 수동 effort 규칙을 구현했다면 ‘Ares 재현’이라고 부르지 않는다. 주 모델 고정+별도 advisor는 추가 선택 실험이다. 설정의 캐시 영향을 먼저 확인한다. [P41](../references/sources.md#p41)

### 신규성·제품 우위를 판단하기 위한 강한 비교군

B0–B6 내부 비교만으로 기존 시스템 대비 이점을 주장할 수 없다. 사용 환경에서 실행 가능한 아래 정책을 추가한다. 원본 배포, 고정 알고리즘 이식, 유사 기능 재구현을 구분해서 보고한다.

| ID | 비교 정책 | 반드시 기록할 설정 |
|---|---|---|
| C1 | Switchyard Stage + user-turn pin / every-request | Stage/judge 사용·후보 두 개 순서·입력 창·trigger·adapter 지원 범위 |
| C2 | Weave planner | 고정 ref·base 추천기·`CorrectedEconomics` off/on·horizon·reuse 미관측 fallback·정책 예외 |
| C3 | vLLM Semantic Router protection | 현재 protection 호출 경로·adaptation off·base 분류기·scope/ID·rescue·cache/remaining prior |
| C4 | 고정 hysteresis·break-even | 동일 upgrade/downgrade 신호, 최소 유지·margin·horizon 가정 |
| C5 | 수동 semantic/profile 또는 kNN utility | memory 허용 여부·같은 embedding/모델 풀·준비 비용·미매칭 처리 |
| C6 | 동일 모델의 effort-only | 같은 모델·지원 effort·캐시 영향·단계/출력/성공·총비용 |

근거: [R06](../references/sources.md#r06), [R07](../references/sources.md#r07), [R11](../references/sources.md#r11), [R14](../references/sources.md#r14), [P39](../references/sources.md#p39), [P11](../references/sources.md#p11), [P41](../references/sources.md#p41).

**두 종류의 비교를 분리한다.** 정책 인과효과 실험은 같은 base selector·입력·harness·후보 풀에 전환 정책만 바꾼다. 제품 end-to-end 실험은 각 시스템의 실제 권장 구성을 쓰되 추천기·기능·학습 artifact·배포 조건 차이를 공개한다. 전자의 개선을 제품 전체 우위로, 후자의 개선을 새 전환 알고리즘만의 효과로 해석하지 않는다.

도구가 있으면 default로 decline하는 Otari v1을 단독 경쟁자로 삼아 이긴 뒤 ‘기존 라우터보다 우수’라 보고하지 않는다. C2/C3처럼 같은 문제를 실제로 다루는 비교군이 중요하다. 과거 `session_aware` 설정이 현재 실행되지 않는데 C3를 켰다고 보고하는 오류도 피한다. [R13](../references/sources.md#r13)

### 추가 구현을 비교군에 연결하는 방법

- Switchyard의 `user_turn`과 `every_request`는 **동일한 판단기를 사용하면서 선택 주기만 바꾸는 별도 실험**에 유용하다. LLM Classifier를 사용했다면 이를 수동 규칙 B2/B3 결과와 섞지 않는다. [R06](../references/sources.md#r06)
- Switchyard Stage의 judge 없는 경로는 B3 규칙 후보로 검토한다. 기존 규칙과 다른 신호·임계값을 쓰면 별도 정책으로 표시하고, 저자가 보정한 권장값과 우리 개발 세트에서 조정한 값을 구분한다.
- B4의 경제성 설계는 Weave planner를 참고한다. legacy·개선 비용식, 남은 단계 가정, 캐시 재사용 비율 미관측 처리, 실제 활성화 플래그를 고정해 보고한다. 예측 적중 여부와 최종 작업 성과를 모두 측정한다. [R07](../references/sources.md#r07)
- Switchyard Escalation을 비교한다면 저가 응답을 생성했지만 폐기한 비용과 judge가 응답을 막고 있는 시간을 포함한다. 도구 행동을 실행하기 전 응답을 교체하는 것과 이미 실행된 행동을 되돌리는 것은 다르다.

## 추가 방법론의 선택 실험

[추가 방법론 비교](../research/alternative-routing-methods.md)에서 나온 후보다. 아래는 미실행 계획이며 B0–B6에 모두 추가하라는 의미가 아니다. 데이터·API·작업 형식 조건이 맞는 것만 고른다.

| 비교 | 고정할 조건 | 추가로 측정할 것 |
|---|---|---|
| kNN utility 대 Avengers-Pro | 같은 support set·임베딩·성능/비용 기록·입력 구성·후보 풀·캐시 정책 | 이웃/클러스터 수 민감도, OOD 오류, 색인·profiling 비용 |
| 수동 semantic 예시 대 수동 규칙 | 같은 모델 매핑·기능 제약·실행 방식 | 미매칭, 잘못된 의미 매칭, 한국어·지시어·주제 전환 |
| Smoothie-Train 대 성능 label 기반 검색 | 분리된 같은 준비 질의, 평가 label은 최종 평가에서만 사용 | 출력 수집 비용, 공유 오답, label 비용을 포함한 초기 총비용 |
| 객관적 verifier 대 자기 검증/일치도 | 같은 저가·고가 모델, 최종 품질·예산 기준 | 반복 샘플 수, 검증 비용, 잘못 수락/불필요 승격, streaming 보류 |
| CP-Router | 선택지·logits 접근 조건, 개발/보정/평가 분리 | coverage와 저가 수락 부분집합 정확도를 별도 측정, 분포 이동 |
| direct LLM 대 agent 선택 | 실제 과업 요구·도구 필요성·양쪽 harness | 작업 완료율, 도구 필요 요청의 잘못된 직접 답변, 초기 경험 수집 비용 |

기존 출력을 재생하는 실험은 **오프라인 선택 품질** 평가라고 표시한다. 실제 API 비용·캐시·도구 실행 경로의 효과는 별도 전체 실행에서 확인해야 한다. 특히 ULab kNN의 최고 성능 label 투표를 가격을 예측하는 kNN utility와 같은 정책 이름으로 보고하지 않는다.

추가 회계 원칙:

- 데이터 수집·색인·성능표/무라벨 출력 구축 비용은 온라인 요청 비용과 분리 보고하고, 예상 트래픽에서 상각한 값도 비교한다.
- CARGO형은 작은 모델의 모든 샘플 비용을 포함한다. cloud 호출 비율이 같다는 사실만으로 비용이 같다고 보지 않는다.
- tool 요청 후보를 여러 개 생성하더라도 부작용 있는 도구를 검증용으로 중복 실행하지 않는다. sandbox·읽기 전용 또는 사전 검증 경계를 정한다.
- Prism 사례처럼 **모든 모델 요청 평균 지연과 새 사용자 턴의 첫 응답 지연**을 분리한다. 도구 후속 요청이 많으면 전체 평균이 사용자가 느끼는 router 대기를 가릴 수 있다. [D09](../references/sources.md#d09)

## 작업과 성공 판정

| 작업군 후보 | 성공 판정 | 주의점 |
|---|---|---|
| 코드 수정 | 사전에 고정한 테스트·회귀 검사 통과 | 단순 patch 생성 여부와 구분 |
| 구조화 추출 | 스키마 + 필드 정답 | JSON 파싱 성공만으로 의미 정확성을 대체하지 않음 |
| 도구 기반 조사 | 질문별 정답·근거 rubric | LLM judge를 쓰면 비용·편향·버전을 명시 |
| 계산·데이터 처리 | 실행 가능한 정답 검사 | 도구 성공과 최종 답의 정확성 모두 확인 |

초기에는 주력 작업군 하나를 정하고 그 안에서 짧은·긴 맥락, 적은·많은 단계, 일시 오류·반복 정체, 한국어·영어, 애매한 최초 질문을 포함한다. 작은 개발 세트는 디버깅용이며 최종 성능 증거로 사용하지 않는다.

## 실행 원칙

1. 모델 후보·제공자·가격·프롬프트·도구·에이전트 harness·정책 버전을 고정한다.
2. 모든 비교군에서 지원되는 프롬프트 캐시를 활성화한다. 캐시 없는 비싼 기준선으로 절감률을 부풀리지 않는다.
3. 개발·평가 작업을 분리한다. 규칙과 임계값을 개발 결과로 조정했으면 수동 튜닝이라고 공개하고 최종 평가에서는 동결한다.
4. 실제 환경에서 작업 전체를 실행한다. 과거 고성능 모델의 고정된 이력만 재생하면 저가 모델 선택으로 달라지는 미래 경로를 놓친다.
5. 모델 선택, 도구 실행, 실패, 재시도, 검증, 사용량을 모두 기록한다. [지표 정의](../design/signals-and-metrics.md)를 따른다.
6. 도구 오류를 환경 오류와 모델이 만든 잘못된 행동으로 나눈다. 제외 규칙은 결과를 보기 전에 정하고 제외 횟수도 보고한다.
7. 실행 순서를 무작위화하고 필요한 반복을 수행한다. 캐시 온도·제공자 부하·서비스 변경의 영향을 구분한다.
8. 성공률 차이는 불확실성과 함께 보고한다. 반복 실행이 같은 문제에서 나왔다는 의존성을 고려해 작업 단위 비교·구간 추정을 사용한다.

고정된 prefix 평가와 실제 전체 실행 평가를 나누는 사례는 [TwinRouterBench P02](../references/sources.md#p02)를 참고한다. 그 논문의 고정 모델 풀·100문제 결과를 우리 작업군의 성능 보장으로 사용하지 않는다.

## 캐시 실험에서 지킬 사항

- `session_id`만 새로 만들었다고 제공자 캐시가 차가워졌다고 단정하지 않는다. 일부 캐시는 요청 간 공통 prefix를 재사용한다.
- cold/warm 여부는 가능하면 usage로 확인한다. 애플리케이션에서 관측할 수 없으면 ‘추정’으로 보고한다.
- A→B→A 실험에서는 A의 캐시를 전환 때 삭제하는 가짜 모델을 기본 가정으로 쓰지 않는다. 만료·접두부 일치·배포 위치를 따로 다룬다.
- 캐시 읽기·쓰기·신규 입력을 분리한다. 전체 input 토큰에 cached 토큰을 다시 더하지 않는다.
- 프롬프트 캐시 실험에 응답 캐시를 섞지 않는다. 이전 답을 그대로 돌려주는 기능은 별도 비교군으로 관리한다.
- 정적 prefix·도구 정의·reasoning 설정의 차이를 기록한다. 모델 선택 외 변경이 캐시를 깨지 않았는지 확인한다.

### H4–H6 진단 시나리오

| 시나리오 | 확인할 문제 |
|---|---|
| 짧게 끝나는 작업 / 긴 도구 루프 / 잔여 길이 예측 오류 | 전환 준비 비용 회수 실패, horizon sensitivity |
| known cache zero / unknown / 실제 hit | 미관측을 hit 또는 miss로 단정해 생기는 전환 오류 |
| A→B→A, TTL 경계, provider/deployment 변경 | 모델별 복귀 캐시·실제 위치·수명 보존 여부 |
| 도구 schema·system prefix·effort 설정 변경 | 모델 이름이 같아도 캐시를 잃는 경우 |
| 외부 5xx / 모델의 잘못된 도구 인자 / 반복 검증 실패 | 환경 장애와 능력 부족 구분, 불필요 승격·rescue |
| provider 전용 state / pending tool pair / 동시 분기 | 전환 금지 조건, 상태 혼합, 중복 도구 부작용 |
| 동일한 짧은 질문 + 서로 다른 assistant/tool 이력 | 의미만 같은 입력과 실제 상태의 차이, H6 |
| judge가 결정을 바꿀 수 없는 상태 / 바꿀 수 있는 상태 | H5의 판정 생략 이득·잘못된 생략·판정 비용 |

비용 예측 오차와 최종 정책 성과를 따로 보고한다. unknown 입력에서 범위 추정을 사용했다면 실측 비용의 범위 포함률·폭을 보고하고 이를 품질 확률이라고 부르지 않는다. 캐시 hit ratio가 높아도 비싼 모델을 지나치게 유지해 총비용이 커질 수 있다.

추가 개발/평가 분리: 같은 episode의 여러 단계, 한국어/영어 번역쌍, 같은 작업 템플릿이 양쪽에 섞여 쉬운 이웃 검색이 되지 않게 한다. memory·threshold·모델 프로필을 평가 결과로 고치면 그 결과는 최종 holdout이 아니다. 가격 변경·모델 추가 시에는 별도 시간축 평가로 보고한다.

벤치마크 원문도 조건을 그대로 쓰지 않는다. DialRouter의 모델 전환 시 완전 cache invalidation은 명시적인 worst-case 가정이고, task-type 연구의 같은 표 선택·평가는 holdout 결과가 아니다. ContinuityBench의 latest-only baseline은 그 실험의 설정이다. [P36](../references/sources.md#p36), [P19](../references/sources.md#p19), [P18](../references/sources.md#p18)

## 중간에 남길 진단

입력 구성도 별도 비교 축으로 둔다. 동일 정책에서 최신 질문만, 첫 작업+최신 질문, 최근 role별 대화 창, 작업 상태+관련 이력을 비교한다. assistant의 제안을 가리키는 ‘이건’, 오래된 참조, 주제 전환, 도구 후속 요청을 포함하고 맥락 누락·판단 비용·최종 작업 성공을 함께 측정한다. 세부 항목은 [입력 맥락 평가](../design/router-input-and-context.md)를 따른다.

- 어떤 규칙으로 선택했는가? 어떤 후보가 왜 제외됐는가?
- 예상 캐시 이득과 실제 usage는 얼마나 달랐는가?
- 저렴한 모델이 더 많은 단계·출력·복구를 만들었는가?
- 상위 모델로 바꾼 이유가 모델 역량 부족이었는가, 외부 도구 장애였는가?
- 라우터 LLM이 차지한 비용과 시간이 절감액을 넘어섰는가?
- 전환을 막아 손해 본 작업과 전환 때문에 손해 본 작업은 각각 무엇인가?

## 보고 형식

결과 문서는 실행일·정책/가격/모델 버전·문제 목록·반복 수·제외 규칙·원시 로그 위치로 시작한다. 성공률과 총비용을 나란히 제시하고, 그 다음 성공 1건당 비용·지연 p50/p95·토큰 회계·실패 유형을 제시한다.

오프라인 점수, 실제 청구액, 실패에 붙인 가상 패널티 비용을 별도 열에 둔다. 점수가 좋은 정책을 발견해도 성공률 하한이나 시간 제약을 위반하면 채택하지 않는다.
